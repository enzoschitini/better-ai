Application Tracing

Use

Guia prático do ApplicationTracing: como criar o tracer, registrar eventos, controlar o que aparece no console e onde os registros são salvos.

Nesta página

    O ApplicationTracing é a porta de entrada do sistema de logs da BetterAI. Esta página mostra o uso no dia a dia; a referência completa de cada classe está em Tracing Core, Logger Engine e Payload Builder.

    #Criar o tracer

    No código da plataforma, cada módulo cria o seu tracer uma única vez, no topo do arquivo, e o reutiliza em todas as funções:

    from src.tracing.tracing_core import ApplicationTracing

tracer = ApplicationTracing(
    flag="DocumentParse",          # nome do logger e da coleção no banco
    file_name="document_parse.py", # aparece em cada registro como file=
    log_file_name="parse",         # arquivo logs/parse.log, quando save_logs está ativo
)
    • flag: identifica a origem dos registros. Vira o nome do logger no console e o nome da coleção quando o registro é salvo no banco. Padrão: "ApplicationTracing".
    • file_name: nome do arquivo de origem, anexado a cada mensagem.
    • log_file_name: nome do arquivo .log em logs/. Padrão: "app".
    • log_id: identificador que acompanha todos os registros da instância. Se omitido, é gerado a partir do horário atual, no formato log_1791458846159946500JItJ. Passe um valor fixo para correlacionar registros de várias instâncias.

    #Registrar eventos

    Os cinco níveis têm a mesma assinatura: func_name, message e um dicionário opcional metadata.

    def run(job_id: str):
    tracer.INFO(func_name="run", message=f"Processing job {job_id}")
    try:
        ...
    except Exception as exc:
        # Dados estruturados vão em metadata, não no texto da mensagem
        tracer.ERROR(
            func_name="run",
            message="Failed to extract content",
            metadata={"job_id": job_id, "error": str(exc)},
        )
        raise
    MétodoQuando usarExemplos
    INFOFluxo normal da aplicação.Início de um processo, conclusão bem-sucedida de uma operação.
    DEBUGDiagnóstico detalhado, útil durante o desenvolvimento.Valores de variáveis, entradas e saídas de funções.
    WARNINGSituação inesperada que não interrompe a execução.Uso obsoleto, lógica de fallback, dados opcionais ausentes.
    ERRORUma operação falhou e afeta a funcionalidade esperada.Chamada de API com falha, exceção capturada.
    CRITICALErro grave, que pode interromper a aplicação.Dependência crítica indisponível, risco de corrupção de dados.

    #O que aparece no console

    Cada registro vira uma linha no stderr, com as partes separadas por |: horário, nível, flag, função, mensagem, metadados, arquivo e log_id.

    Console
    2026-10-08 08:27:26,159 | ERROR | DocumentParse | run() | Failed to extract content | file=document_parse.py | log_id=log_1791458846159946500JItJ

    Por padrão, só ERROR e CRITICAL aparecem. Com show_info_logs=False (o padrão), o console descarta INFO, DEBUG e também WARNING. Ative show_info_logs para ver todos os níveis.

    Os metadados só entram na linha com show_metadata=True; sem ele, ficam de fora mesmo em um ERROR:

    Console
    2026-10-08 08:27:26,159 | INFO | DocumentParse | run() | Completed processing | metadata={'job_id': 'job_42'} | file=document_parse.py | log_id=log_1234

    Com format_metadata=True, os metadados saem como JSON indentado, em várias linhas, em vez do dicionário em uma linha só.

    #Salvar os registros

    #Em arquivo

    Com save_logs=True, cada registro também é gravado em logs/<log_file_name>.log. A pasta logs/ é criada no diretório de onde o processo foi iniciado. O arquivo recebe todos os níveis, independentemente de show_info_logs, e o texto é a mesma linha do console, sem as cores.

    #No banco NoSQL

    Com save_mongo=True, cada registro também é enviado ao DocumentStore, no banco application_tracings, numa coleção com o nome da flag. O backend é escolhido por NOSQL_BACKEND:

    • mongo: grava no MongoDB.
    • local (padrão): grava em JSON, em data/application_tracings/<flag>.json.

    O documento salvo traz os metadados completos, mesmo com show_metadata=False:

    {
  "log_id": "log_1234",
  "level": "ERROR",
  "flag": "DocumentParse",
  "func_name": "run",
  "message": "Failed to extract content",
  "metadata": {"job_id": "job_42"},
  "file_name": "document_parse.py",
  "time": "2026-10-08 08:27:26,159"
}

    O backend local acrescenta os campos _id e _created_at.

    #Configurar por variáveis de ambiente

    As opções de exibição e gravação também podem vir do .env, sem mudar o código:

    VariávelParâmetro
    SHOW_INFO_LOGSshow_info_logs
    SHOW_METADATAshow_metadata
    SAVE_LOGSsave_logs
    SAVE_MONGOsave_mongo
    FORMAT_METADATAformat_metadata
    NOSQL_BACKENDBackend de save_mongo: mongo ou local (padrão).

    Quando a mesma opção é definida em mais de um lugar, vale a primeira desta lista:

    1. O argumento passado na chamada de log, só para aquela chamada.
    2. O argumento True no construtor: ele ignora a variável de ambiente.
    3. A variável de ambiente, quando o construtor recebeu False (o padrão).
    4. False, se nada foi definido.

    As variáveis SHOW_*, SAVE_* e FORMAT_METADATA são lidas uma vez, quando o tracer é criado: mudar o ambiente depois não afeta um tracer que já existe. NOSQL_BACKEND é lida a cada gravação.

    Só true e false. Os valores aceitos são true e false, sem diferenciar maiúsculas. Qualquer outro valor, como 1 ou yes, gera KeyError na criação do tracer.

    #Sobrescrever em uma chamada

    Os métodos de log aceitam show_info_logs, show_metadata e save_logs, que valem só para aquela chamada:

    # Mostra este INFO mesmo com show_info_logs=False na instância
tracer.INFO(func_name="run", message="Checkpoint", show_info_logs=True)

# Grava só este registro em arquivo, com os metadados na linha
tracer.ERROR(
    func_name="process_payment",
    message="Payment failed",
    metadata={"user_id": 123},
    save_logs=True,
    show_metadata=True,
)

    save_mongo não funciona por chamada. O parâmetro existe na assinatura dos métodos, mas a gravação no banco segue sempre o valor da instância: save_mongo=True numa chamada não grava, e save_mongo=False não impede a gravação.

    #Testar

    O arquivo src/tracing/tracing_test.py emite um registro de cada nível. Rode a partir da raiz do projeto:

    python -m src.tracing.tracing_test

    Com a configuração padrão, só os registros ERROR e CRITICAL aparecem. Defina SHOW_INFO_LOGS=true no .env para ver os cinco.
