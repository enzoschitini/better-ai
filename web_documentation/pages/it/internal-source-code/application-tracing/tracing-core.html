Application Tracing

Tracing Core

Questa è una documentazione dettagliata e didattica della classe ApplicationTracing, progettata per facilitare l'implementazione dell'osservabilità nei sistemi Python.

In questa pagina

    #Panoramica

    La classe ApplicationTracing agisce come una Facciata (Facade) per la gestione dei log. Invece di occuparsi direttamente di librerie complesse o configurazioni di basso livello, lo sviluppatore usa questa classe per standardizzare come i messaggi vengono registrati, mostrati e archiviati.

    L'obiettivo principale è garantire che tutti i log dell'applicazione seguano la stessa struttura, facilitando la ricerca dei guasti (troubleshooting) e l'analisi dei dati in strumenti come MongoDB o visualizzatori di file di log.

    #Flusso di Esecuzione

    Il flusso di funzionamento della classe segue queste fasi:

    1. Istanziazione: Lo sviluppatore crea l'oggetto definendo le configurazioni globali (es: se salvare in MongoDB, se mostrare i metadati sulla console).
    2. Incapsulamento: Il costruttore inizializza internamente il LoggerEngine, che è il vero motore di elaborazione.
    3. Chiamata di Metodo: Quando chiami un metodo come .INFO() o .ERROR(), i parametri passati (messaggio, metadati) vengono inviati al motore.
    4. Sovrascrittura Dinamica: Ogni metodo di log permette di sovrascrivere momentaneamente le configurazioni globali (es: il sistema non salva i log INFO per impostazione predefinita, ma puoi forzare il salvataggio di un log specifico).
    5. Uscita Multicanale: Il log viene elaborato e inviato contemporaneamente alla console, al file locale o al database, secondo la configurazione.

    #Tabella dei Metodi

    MetodoLivello di GravitàUso Consigliato
    __init__N/AConfigurazione iniziale e setup dei driver di uscita.
    INFOInformativoTraguardi di successo e flusso normale (es: "Elaborazione completata").
    DEBUGBassoDettagli tecnici per gli sviluppatori (es: valori di variabili).
    WARNINGMedioSituazioni inattese che non impediscono l'esecuzione (es: "API lenta").
    ERRORAltoErrori in funzionalità specifiche (es: "Invio e-mail non riuscito").
    CRITICALUrgenteProblemi che possono far cadere il sistema (es: "Database offline").

    #Architettura e Spunti

    • Separazione delle Responsabilità: La classe non sa come scrivere in MongoDB; delega questa responsabilità al LoggerEngine. Questo facilita la manutenzione futura.
    • Flessibilità Granulare: Il design permette di avere un comportamento globale, ma piena flessibilità su ogni riga di codice tramite gli argomenti opzionali dei metodi.
    • Osservabilità Strutturata: L'uso dell'argomento metadata (dizionario) incoraggia il log strutturato (JSON), molto più facile da indicizzare e cercare rispetto a semplici stringhe di testo.
    • Tracciabilità: Il parametro log_id permette di correlare i log di una stessa transazione che attraversa funzioni o file diversi.

    #Documentazione Tecnica

    #Classe ApplicationTracing

    #Descrizione

    Classe responsabile di astrarre e standardizzare l'uso dei log all'interno dell'applicazione. Incapsula la logica complessa del logging e fornisce un'interfaccia semplificata allo sviluppatore.

    #Argomenti del Costruttore

    • log_id (str): ID univoco per il tracciamento del flusso.
    • flag (str): Marcatore per categorizzare i log.
    • file_name (str): Contesto del file di origine.
    • log_file_name (str): Nome del file .log di destinazione.
    • show_info_logs (bool): Abilita/Disabilita i log di livello INFO sulla console.
    • show_metadata (bool): Definisce se i dettagli tecnici compaiono sulla console.
    • save_logs (bool): Se True, scrive su file fisico.
    • save_mongo (bool): Se True, rende persistente nel database.
    • format_metadata (bool): Applica una formattazione visiva ai metadati.

    #Metodi

    #1. INFO / DEBUG / WARNING / ERROR / CRITICAL

    (I metodi condividono la stessa firma per mantenere la coerenza)

    Descrizione

    Registrano un messaggio al livello di gravità corrispondente, gestendo l'archiviazione e la visualizzazione secondo le regole definite nell'istanza.

    Argomenti

    • func_name (Optional[str]): Nome della funzione in cui è avvenuto l'evento.
    • message (Optional[str]): Testo esplicativo del log.
    • metadata (Optional[Dict]): Dizionario con dati extra (es: {"user_id": 123}).
    • save_logs (Optional[bool]): Sovrascrive la configurazione globale di salvataggio su file.
    • save_mongo (Optional[bool]): Sovrascrive la configurazione globale di salvataggio in MongoDB.
    • show_info_logs (Optional[bool]): Forza la visualizzazione o l'occultamento dei log INFO.
    • show_metadata (Optional[bool]): Forza la visualizzazione o l'occultamento dei metadati.

    Valori di ritorno

    • None: Il metodo esegue la registrazione (effetto collaterale) e non restituisce dati.

    Raises

    • Exception: Può propagare errori di connessione al database o di permesso di scrittura su disco originati nel LoggerEngine.

    Esempi

    from src.tracing.tracing_core import ApplicationTracing

# Inicialização
tracer = ApplicationTracing(save_logs=True, log_id="TR-9952")

# Uso simples
tracer.INFO(
    func_name="create_user",
    message="App Init"
)

tracer.DEBUG(
    func_name="create_user",
    message="User created",
    metadata={"user": "Enzo"},
    #save_logs=False
    #show_metadata=False
)

tracer.WARNING(
    func_name="create_user",
    message="User created",
    metadata={"user": "Enzo"},
)

tracer.ERROR(
    func_name="create_user",
    message="User created",
    metadata={"user": "Enzo"},
)

tracer.CRITICAL(
    func_name="create_user",
    message="User created",
    metadata={"user": "Enzo"},
)

# Debug forçando salvamento no Mongo apenas para esta linha
tracer.DEBUG(message="Checkpont técnico", save_mongo=True)
