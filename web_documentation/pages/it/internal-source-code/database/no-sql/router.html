Router

Questa documentazione descrive in dettaglio la classe DocumentStore, un componente essenziale per la persistenza dei dati nella tua architettura, progettato per offrire flessibilità e disaccoppiamento.

In questa pagina

    #Panoramica

    La classe DocumentStore agisce come Router e Proxy per le operazioni sui database NoSQL. Il suo obiettivo principale è astrarre la complessità di quale database venga utilizzato (MongoDB o JSON Locale).

    Questo permette agli sviluppatori di scrivere una sola volta il codice della logica di business, potendo cambiare l'archiviazione semplicemente modificando una variabile d'ambiente o un parametro iniziale, il che è ideale per passare da un ambiente di Produzione (MongoDB) a uno di Sviluppo/Test (Locale).

    #Flusso di Esecuzione

    Il funzionamento della classe segue una logica in tre semplici fasi:

    1. Istanziazione: Alla creazione dell'oggetto, il codice verifica l'argomento backend o la variabile d'ambiente NOSQL_BACKEND.
    2. Fabbrica (Factory): Il metodo interno _initialize_manager decide quale classe gestore istanziare (MongoDBManager o LocalManager).
    3. Delega (Proxy): Quando viene chiamato un metodo come save_payload, DocumentStore non elabora direttamente il dato; "passa la palla" al gestore istanziato nella fase 2.

    #Tabella dei Metodi

    MetodoTipoDescrizione Breve
    __init__CostruttoreDefinisce il backend e inizializza il gestore.
    _initialize_managerPrivatoLogica decisionale (Factory) per scegliere il backend.
    save_payloadProxyInserisce nuovi documenti nel database.
    fetch_documentsProxyCerca e recupera documenti filtrati.
    update_documentsProxyAggiorna i dati dei documenti esistenti.
    delete_documentsProxyRimuove documenti dal database.

    #Architettura e Insights

    • Pattern Proxy: La classe funge da interfaccia unificata. Il codice che chiama DocumentStore non ha bisogno di sapere come funziona MongoDB, ma solo cosa vuole fare.
    • Pattern Factory: La logica di creazione dell'oggetto database è centralizzata in un unico punto, facilitando l'aggiunta di nuovi backend in futuro (come Redis o DynamoDB).
    • Disaccoppiamento: L'uso di args e *kwargs nei metodi permette all'interfaccia di essere abbastanza generica da accettare i diversi parametri richiesti da backend distinti senza rompere la firma dei metodi.

    #Dettaglio della Classe

    #Classe DocumentStore

    Descrizione

    Una classe di astrazione di alto livello che gestisce la persistenza dei documenti NoSQL. Centralizza le operazioni CRUD (Create, Read, Update, Delete) e delega l'esecuzione a backend specifici in base alla configurazione.

    Argomenti

    • backend (Optional[str]): Una stringa che indica il backend desiderato. Valori accettati: "mongo" oppure "local". Se None, cerca nella variabile d'ambiente NOSQL_BACKEND.

    #Metodi

    #1. _initialize_manager

    Descrizione

    Metodo interno che decide quale implementazione di database verrà caricata in memoria.

    Argomenti

    • Non ha argomenti diretti (utilizza lo stato di self.backend).

    Valori di ritorno

    • Union[MongoDBManager, LocalManager]: Un'istanza della classe responsabile della comunicazione reale con il database.

    Raises

    • ValueError: Se il backend indicato non è "mongo" o "local".

    #2. save_payload

    Descrizione

    Esegue l'inserimento di un documento o di un carico di dati nel backend selezionato.

    Argomenti

    • args / *kwargs: Di solito includono il nome del database, il nome della collezione/tabella e il dizionario dei dati (payload).

    Valori di ritorno

    • dict: Informazioni sull'esito dell'operazione (es: ID del documento inserito).

    Raises

    • Exception: Propaga gli errori specifici del driver di connessione al database.

    Esempi

    store = DocumentStore(backend="local")
store.save_payload(db="app", collection="logs", data={"status": "sucesso"})

    #3. fetch_documents

    Descrizione

    Interroga il database per restituire i documenti che corrispondono ai criteri indicati.

    Argomenti

    • args / *kwargs: Filtri di ricerca (es: {"id": 123}).

    Valori di ritorno

    • list: Una lista contenente i documenti trovati (dizionari).

    Esempi

    # Busca todos os usuários com nome Enzo
users = store.fetch_documents("mydb", "users", {"name": "Enzo"})

    #4. update_documents

    Descrizione

    Modifica i documenti esistenti nel database in base a un criterio di selezione.

    Argomenti

    • args / *kwargs: Filtro di ricerca e nuovi dati da applicare.

    Valori di ritorno

    • dict: Riepilogo dell'operazione (quantità di campi modificati).

    Esempi

    store.update_documents("mydb", "users", {"name": "Enzo"}, {"active": True})

    #5. delete_documents

    Descrizione

    Rimuove uno o più documenti dal database.

    Argomenti

    • args / *kwargs: Filtri per identificare quali documenti devono essere eliminati.

    Valori di ritorno

    • dict: Conferma della rimozione.

    Esempi

    store.delete_documents("mydb", "users", {"name": "Enzo"})

    #Uso

    import json
from src.database.no_relational_db.router import DocumentStore

manager = DocumentStore(backend="local")

manager.save_payload("mydb", "users", {"name": "Enzo"})

docs = manager.fetch_documents("mydb", "users", {"name": "Enzo"})
print(json.dumps(docs, indent=4))

manager.update_documents("mydb", "users", {"name": "Enzo"}, {"age": 25})

manager.delete_documents("mydb", "users", {"name": "Enzo"})

response = manager.save_payload("mydb", "users", {"name": "Enzo"})
print(response["inserted_id"])
