ApplicationTracing è il punto d’ingresso del sistema di log di BetterAI. Questa pagina mostra l’uso quotidiano; il riferimento completo di ogni classe si trova in Tracing Core, Logger Engine e Payload Builder.

Creare il tracer

Nel codice della piattaforma, ogni modulo crea il proprio tracer una sola volta, in cima al file, e lo riutilizza in tutte le funzioni:


from src.tracing.tracing_core import ApplicationTracing

tracer = ApplicationTracing(
    flag="DocumentParse",          # nome del logger e della collezione nel database
    file_name="document_parse.py", # compare in ogni record come file=
    log_file_name="parse",         # file logs/parse.log, quando save_logs è attivo
)
  • flag: identifica l’origine dei record. Diventa il nome del logger nella console e il nome della collezione quando il record viene salvato nel database. Predefinito: "ApplicationTracing".
  • file_name: nome del file di origine, aggiunto a ogni messaggio.
  • log_file_name: nome del file .log in logs/. Predefinito: "app".
  • log_id: identificatore che accompagna tutti i record dell’istanza. Se omesso, viene generato dall’orario corrente, nel formato log_1791458846159946500JItJ. Passa un valore fisso per correlare i record di più istanze.

Registrare eventi

I cinque livelli hanno la stessa firma: func_name, message e un dizionario opzionale metadata.


def run(job_id: str):
    tracer.INFO(func_name="run", message=f"Processing job {job_id}")
    try:
        ...
    except Exception as exc:
        # I dati strutturati vanno in metadata, non nel testo del messaggio
        tracer.ERROR(
            func_name="run",
            message="Failed to extract content",
            metadata={"job_id": job_id, "error": str(exc)},
        )
        raise
MetodoQuando usarloEsempi
INFOFlusso normale dell’applicazione.Avvio di un processo, completamento riuscito di un’operazione.
DEBUGDiagnostica dettagliata, utile durante lo sviluppo.Valori di variabili, input e output di funzioni.
WARNINGSituazione inattesa che non interrompe l’esecuzione.Uso deprecato, logica di fallback, dati opzionali mancanti.
ERRORUn’operazione è fallita e compromette la funzionalità attesa.Chiamata API fallita, eccezione catturata.
CRITICALErrore grave, che può interrompere l’applicazione.Dipendenza critica non disponibile, rischio di corruzione dei dati.

Cosa compare nella console

Ogni record diventa una riga su stderr, con le parti separate da |: orario, livello, flag, funzione, messaggio, metadati, file e log_id.


2026-10-08 08:27:26,159 | ERROR | DocumentParse | run() | Failed to extract content | file=document_parse.py | log_id=log_1791458846159946500JItJ

Per impostazione predefinita compaiono solo ERROR e CRITICAL. Con show_info_logs=False (il predefinito), la console scarta INFO, DEBUG e anche WARNING. Attiva show_info_logs per vedere tutti i livelli.

I metadati entrano nella riga solo con show_metadata=True; senza, restano fuori anche in un ERROR:


2026-10-08 08:27:26,159 | INFO | DocumentParse | run() | Completed processing | metadata={'job_id': 'job_42'} | file=document_parse.py | log_id=log_1234

Con format_metadata=True, i metadati escono come JSON indentato, su più righe, invece del dizionario su una sola riga.

Salvare i record

Su file

Con save_logs=True, ogni record viene scritto anche in logs/<log_file_name>.log. La cartella logs/ viene creata nella directory da cui è stato avviato il processo. Il file riceve tutti i livelli, indipendentemente da show_info_logs, e il testo è la stessa riga della console, senza colori.

Nel database NoSQL

Con save_mongo=True, ogni record viene inviato anche al DocumentStore, nel database application_tracings, in una collezione con il nome della flag. Il backend è scelto da NOSQL_BACKEND:

  • mongo: scrive su MongoDB.
  • local (predefinito): scrive in JSON, in data/application_tracings/<flag>.json.

Il documento salvato contiene i metadati completi, anche con show_metadata=False:


{
  "log_id": "log_1234",
  "level": "ERROR",
  "flag": "DocumentParse",
  "func_name": "run",
  "message": "Failed to extract content",
  "metadata": {"job_id": "job_42"},
  "file_name": "document_parse.py",
  "time": "2026-10-08 08:27:26,159"
}

Il backend local aggiunge i campi _id e _created_at.

Configurare tramite variabili d'ambiente

Le opzioni di visualizzazione e salvataggio possono arrivare anche dal .env, senza modificare il codice:

VariabileParametro
SHOW_INFO_LOGSshow_info_logs
SHOW_METADATAshow_metadata
SAVE_LOGSsave_logs
SAVE_MONGOsave_mongo
FORMAT_METADATAformat_metadata
NOSQL_BACKENDBackend di save_mongo: mongo o local (predefinito).

Quando la stessa opzione è definita in più punti, vale la prima di questo elenco:

  1. L’argomento passato nella chiamata di log, solo per quella chiamata.
  2. L’argomento True nel costruttore: ignora la variabile d’ambiente.
  3. La variabile d’ambiente, quando il costruttore ha ricevuto False (il predefinito).
  4. False, se non è stato definito nulla.

Le variabili SHOW_*, SAVE_* e FORMAT_METADATA vengono lette una sola volta, quando il tracer viene creato: cambiare l’ambiente dopo non ha effetto su un tracer già esistente. NOSQL_BACKEND viene letta a ogni salvataggio.

Solo true e false. I valori accettati sono true e false, senza distinzione tra maiuscole e minuscole. Qualsiasi altro valore, come 1 o yes, genera KeyError alla creazione del tracer.

Sovrascrivere in una chiamata

I metodi di log accettano show_info_logs, show_metadata e save_logs, che valgono solo per quella chiamata:


# Mostra questo INFO anche con show_info_logs=False nell'istanza
tracer.INFO(func_name="run", message="Checkpoint", show_info_logs=True)

# Scrive su file solo questo record, con i metadati nella riga
tracer.ERROR(
    func_name="process_payment",
    message="Payment failed",
    metadata={"user_id": 123},
    save_logs=True,
    show_metadata=True,
)

save_mongo non funziona per singola chiamata. Il parametro esiste nella firma dei metodi, ma il salvataggio nel database segue sempre il valore dell’istanza: save_mongo=True in una chiamata non salva, e save_mongo=False non impedisce il salvataggio.

Provare

Il file src/tracing/tracing_test.py emette un record per ogni livello. Eseguilo dalla radice del progetto:


python -m src.tracing.tracing_test

Con la configurazione predefinita compaiono solo i record ERROR e CRITICAL. Imposta SHOW_INFO_LOGS=true nel .env per vederli tutti e cinque.
